# FP42 BREAKER lane - why wp2 confirmed path traversal on weakrand-00/BenchmarkTest00042

Question: wp2 (seal `82f55903`, artifact `docs/benchmarks/wp2_q047_fixed_oracle_claims.json`) reported

```
path_traversal | Path traversal in POST body field 'password' | https://owaspbench:8443/benchmark/weakrand-00/BenchmarkTest00042
```

`BenchmarkTest00042` is a weakrand case, not vulnerable. It is the only FP in that run, and it could
not be reproduced by driving `_run_web_probes` against that URL standalone.

Status: **REPRODUCED**. Root cause identified and MEASURED. This lane fixes nothing; the patch is
written out below for the owner of `agent/web_security.py` to apply.

---

## 1. The first difference: the mission never probed the URL in the finding row

No `<form>` in that body, so `form_xss.parse_forms(baseline["body"])` returns `[]` and the whole
POST-body traversal branch of `_run_web_probes` is skipped. That alone explains "standalone run
returns ZERO findings": the standalone driver was pointed at a page that has no POST-body carrier.

The form lives on the **`.html` sibling** that a mission crawls:

```
$ ... httpx.get('.../weakrand-00/BenchmarkTest00042.html')
```

`fm["action"]` is the servlet, `text_fields` are `[email, password, BenchmarkTest00042]`. That is
where the field name `'password'` in the finding row comes from, and why `target` is the servlet
while the page actually scanned was `...00042.html`.

**So: probe the `.html` page, not the servlet.** That is the reproduction sequence.

## 2. Reproduction

Driver (scratchpad, not committed) calls the real engine:

```python
scope = ScopeEngine(); scope.load_manual(["owaspbench:8443"], [], "bench")
reg = tools.ToolRegistry(scope, mission_id=None, lab_mode=True)
res = await reg._run_web_probes({"url": ".../weakrand-00/BenchmarkTest00042.html", "lab_mode": True})
```

MEASURED, 3 trials:

```

trial 1: findings=1 traversal=1
```

It is **non-deterministic** - it fires on some runs and not others, and the field it lands on is
whichever of `email` / `password` / `BenchmarkTest00042` wins the dice (the POST-body field loop
does not `break` on a differential hit, so all three fields are tried). The mission got `password`;
this repro got `email`. Same defect.

The "evidence" `'90997'` is a fragment of the servlet's random number. That is the tell.

## 3. Which of the four call sites emitted it

`_traversal_finding` at `agent/tools.py:3321`, i.e. inside `_traversal_differential`, reached from
the **POST-body differential** call site at `agent/tools.py:~5885`. Confirmed by the emitted verdict:
`oracle=existence-differential`, `confidence=confirmed`, and the reason text ends in
`"- and it REPRODUCED on a repeat of the same request"`, which is written only by `graded()` in
`web_security.analyze_traversal_differential`.

So the Q-047 repeat control **was in force and was satisfied**. It did not fail to run; it failed to
discriminate. The other three sites (`analyze_traversal_pair` for query / POST body / header) are not
implicated here.

## 4. Root cause - three facts that only combine inside `_run_web_probes`

**(a) `ToolRegistry._http` builds a NEW `httpx.AsyncClient` per request** (`agent/tools.py:3210`,
`async with _target_client(...) as c:`; `browser_engine.rate_limited_async_client` constructs a fresh
`AsyncClient` every call, it does not cache). There is therefore **no cookie jar shared between the
four differential requests**.

The endpoint's state is a cookie (`rememberMe00042` + the matching session attribute). With no cookie
carried, **every** request is a first request, so every response is the state-establishing body -
and that body embeds a fresh `nextInt()` value. The endpoint is not "stateful then steady" under the
engine's transport; it is **fresh-random on every single request**.

This is exactly why the manual standalone reproduction could not see it. A hand-driven
`httpx.AsyncClient` reused across the four sends keeps the cookie, so request 1 is
`has been remembered ... -272252341` (len 164) and requests 2-4 are the CONSTANT
`Welcome back: SafeIngrid00042` (len 102, all three identical). Under a shared client the page is
deterministic; under `_http` it is not. **The transport, not the oracle, is the difference between
the mission and the standalone run.**

**(b) The determinism control samples only two responses and has a 3-character floor.**
`analyze_traversal_differential` step (1) is
`if a_st != b_st or unexplained_divergence(a_text, b_text, payloads): return None`.
`unexplained_divergence` runs `SequenceMatcher` over the redacted bodies and returns a chunk only if
some opcode chunk has `>= min_chars (3)` alphanumerics. Two random decimal integers of ~10 digits are
frequently chopped by SequenceMatcher into many 1-2 character opcode chunks, in which case
`unexplained_divergence` returns `None` and a **nondeterministic page is certified deterministic**.

**(c) The repeat control cannot catch this class.** Q-047's repeat was designed against a
FIRST-REQUEST artifact: a first response differs, a repeat does not, so the divergence dies. Here the
artifact is per-request, so the repeat diverges from both absents exactly as the original `exists`
did. `holds=True`, `graded()` upgrades to confirmed, and the reason gains the words "it REPRODUCED".
The repeat control is a control for state, not for randomness, and it is being asked to do the job of
the determinism control that (b) let through.

Note this is the mirror image of the hypothesis already killed as "page nondeterminism": the page IS
nondeterministic, but only under the engine's fresh-client-per-request transport, which is why 75/75
shared-client trials saw nothing.

## 5. Hypotheses tested and killed

- `max_twins` / second twin running against state the first twin changed - NOT the cause. There is no
  carried state at all (see 4a); every request is independent.
- Session shared with earlier engines in the mission - NOT the cause, same reason. `_http` shares no
  cookie jar with anything.
- Ungated fourth producer (`analyze_traversal_pair` emitting proven wording) - NOT implicated for this
  row (see 3). It remains a separate, real hole: `analyze_traversal_pair` returns
  `confidence=confirmed` on `file-content-signature`, and all three of its call sites feed
  `_traversal_finding` directly with no repeat control. Not the defect here.

## 6. The exact row, reproduced - and why the field is `password`

The 3-trial repro above landed on `email`, not `password`, because it ran with `lab_mode=True`. The
POST-body branch has `_budget = 12` and, in lab mode, `_tp` is 14 payloads
(`7 TRAVERSAL_SAFE_PAYLOADS + 7 TRAVERSAL_LAB_PAYLOADS`, MEASURED). Field 1 (`email`) burns all 12 on
the single-request loop, then `_budget -= 3`, then the field loop's `if _budget <= 0: break` fires -
so with `lab_mode=True` **only `email` is ever reachable**.

With `lab_mode` False, `_tp` is 7, so `email` leaves budget 5, `-3` leaves 2, and field 2
(`password`) runs. MEASURED, 40 trials, `lab=False`:

```
trial 0   confirmed | Path traversal in POST body field 'email'    | .../weakrand-00/BenchmarkTest00042
trial 0   confirmed | Path traversal in POST body field 'password' | .../weakrand-00/BenchmarkTest00042
trial 14  confirmed | Path traversal in POST body field 'password' | .../weakrand-00/BenchmarkTest00042
trial 29  confirmed | Path traversal in POST body field 'password' | .../weakrand-00/BenchmarkTest00042
trial 32  confirmed | Path traversal in POST body field 'email'    | .../weakrand-00/BenchmarkTest00042
trial 32  confirmed | Path traversal in POST body field 'password' | .../weakrand-00/BenchmarkTest00042
lab=False trials=40 hit_titles={'...email': 2, '...password': 4} total_hits=6
```

That is the wp2 row, byte for byte, including `confidence=confirmed`. **`password` hits 4/40 = 10%
of pages scanned.** `lab_mode=True`, 20 trials: 0/20 (only `email` reachable, ~5% per page).

## 7. Rate measurement of the underlying oracle failure

MEASURED. 300 real responses fetched with a NEW client per request (what `_http` does), then a
5000-draw Monte Carlo of `analyze_traversal_differential` over random 4-tuples of them:

```
pool=300 distinct=300
determinism control PASSED : 169 / 5000 = 3.38%
differential CONFIRMED     : 149 / 5000 = 2.98%
evidence lengths seen      : {3: 48, 4: 28, 5: 31, 6: 19, 7: 13, 8: 8, 9: 2}
NEGATIVE CONTROL (random int masked) CONFIRMED: 0 / 5000
```

- 300/300 responses distinct - the endpoint is fully nondeterministic under this transport.
- The determinism control certifies it deterministic 3.38% of the time, and 88% of those go on to
  confirm.
- Every "evidence" string is 3-9 characters, i.e. a fragment of the random integer. The `min_chars=3`
  floor in `unexplained_divergence` is exactly what is being squeaked past: SequenceMatcher chops two
  random 9-10 digit numbers into opcode chunks, and 3.4% of the time every chunk has fewer than 3
  alphanumerics, so the function returns `None` and the caller reads that as "identical".
- NEGATIVE CONTROL: masking the random integer with `re.sub(r"-?\d{4,}", "N", body)` drops confirms
  to **0/5000**. The random integer is the sole cause; nothing else in the response contributes.
