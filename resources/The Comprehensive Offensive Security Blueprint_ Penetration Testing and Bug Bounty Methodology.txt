The Comprehensive Offensive Security Blueprint: Penetration Testing and Bug Bounty Methodology #### 1. Foundational Architecture: The Client-Server Exchange A master-level security assessment begins with the internet’s "plumbing." One cannot dismantle an application’s logic without first understanding the mechanics of how data traverses the stack. The Client-Server model and the Domain Name System (DNS) are the non-negotiable foundations; they dictate the rules of engagement. Without this, a tester is merely throwing payloads at a black box. A senior architect views every request as a structured exchange and every port as a strategic gateway. ##### The Mechanics of Service Forwarding The internet operates on the Client-Server model , where clients (browsers) request resources and servers provide them. Port numbers are the logical divisions that allow a server to provide multiple services simultaneously, forwarding incoming messages to the correct service for processing. | Port Number | Default Service | Security Implications & Architect's Perspective | | ------ | ------ | ------ | | 80 | HTTP | Unencrypted traffic; high risk of eavesdropping and MITM. | | 443 | HTTPS | Encrypted version of HTTP; requires CA certificates for inspection. | | 22 | SSH | Secure remote access; target for credential brute-forcing and key theft. | | 25 | SMTP | Mail transfer; can be probed for internal routing and user enumeration. | ##### Strategic HTTP Analysis Communication is governed by HyperText Transfer Protocol (HTTP) . Every exchange consists of a Request (Request Line, Headers, Body) and a Response. During a hunt, HTTP Status Codes are your primary indicators of server behavior: * 200 OK: Successful request; the target is rendered. * 403 Forbidden: A critical hunt indicator . This code suggests the resource exists but access is denied. To an architect, this indicates sensitive data is present that could be reached by bypassing access controls or misconfigured filters. * 404 Not Found: Resource missing, helpful for mapping the structure. * 3XX (Redirect): Prime target for open-redirect and phishing-based vulnerabilities. These protocols facilitate the session management and encoding practices necessary for maintaining persistence, which we exploit in the next phase. #### 2. Session Management and Security Controls Session persistence is a strategic necessity that creates a massive attack surface. Security controls like the Same-Origin Policy (SOP) are designed to protect data integrity, but flaws in implementation—specifically in token handling—allow for total session takeover. ##### Authentication Models: Sessions vs. Tokens * Session-based: The server stores information and issues a unique Session ID via a cookie. * Token-based (JWT): The server encodes identity directly into a token. A JWT consists of a Header (algorithm), Payload (claims), and Signature (integrity check). ##### The "So What?" of JWT Vulnerabilities JWTs are prone to forgery if the signature verification is weak: * Algorithm "none" Bypass: Changing the alg field to none can trick servers into accepting unsigned tokens. * RSA to HMAC Switching: If a server expects RSA (public/private) but accepts HMAC (shared secret), an attacker can sign a forged token with the server's public key . The server, now treating the key as a shared HMAC secret, validates the forged signature. ##### The Fundamental Rule: Same-Origin Policy (SOP) SOP is the primary rule preventing a script on attacker.com from reading data from onlinebank.com. An origin is defined by Protocol, Hostname, and Port . * Same Origin: https://example.com/page1 and https://example.com/page2. * Different Origin: * http://example.com (Different protocol: HTTP vs. HTTPS). * https://vulnerable.com (Different hostname). * https://example.com:8080 (Different port). Understanding these controls allows us to transition into the reconnaissance phase, where we map how these rules are applied across the organization's landscape. #### 3. Strategic Reconnaissance: Mapping the Attack Surface Reconnaissance defines the attack surface. The breadth of discovery dictates the depth of exploitation; if you cannot see a subdomain, you cannot test it. ##### Multi-Tiered Discovery Methodology 1. WHOIS & Reverse WHOIS: Execute whois to identify owners. Use Reverse WHOIS to find obscure or internal domains registered under the same email or organization. 2. IP-to-ASN Strategy: Perform IP-to-ASN translations to identify the NetRange (e.g., 157.240.0.0 - 157.240.255.255). Deduce that any IP within that block is a valid target owned by the organization. 3. Certificate Parsing: Use crt.sh or Censys to find "Subject Alternative Names" on SSL certificates, revealing hidden hostnames. ##### Advanced Google Dorking * site:example.com – Limit to target. * inurl:admin – Find admin panels. * filetype:log – Locate logs. * intitle:"index of" – Find directory listings. Strategic Hunt: site:example.com ext:txt password or site:example.com inurl:app/kibana. ##### Active vs. Passive Enumeration Contrast Active Scanning (direct engagement using Nmap , Masscan , or Gobuster DNS mode ) with Passive Discovery (using Shodan or Censys to view data without touching the target). ##### GitHub and S3 Strategic Discovery * GitHub Recon: Use Gitrob or TruffleHog to scan for hardcoded secrets. * S3 Bucket Discovery: Use GrayhatWarfare to find buckets. Execute aws s3 ls s3://BUCKET_NAME/ to verify public read access. If you find leaked credentials, use KeyHacks to verify their validity against target services. #### 4. Parameter Discovery and Technical Fingerprinting Once the surface is mapped, narrow your focus by identifying hidden entry points and fingerprinting the underlying tech stack to match against known CVEs. ##### Hidden Parameter Discovery Execute the Arjun HTTP parameter discovery suite. Arjun acts as a heuristic scanner , identifying parameters like go button or search_for that do not appear in the UI. Focus on finding "parameter reflection," where input is rendered in the response—this is the precursor to XSS and SQLi. ##### Tech Stack Fingerprinting Analyze headers and files to reveal the backend framework: * Headers: Server: Apache, X-Powered-By: PHP, or X-Generator: Drupal 8. * Cookies: PHPSESSID (PHP) or JSESSIONID (Java). * File Signatures: A directory named jinja2 reveals a Django/Python stack; /phpmyadmin confirms PHP. #### 5. Core Vulnerability Exploitation: XSS, Redirects, and CSRF Client-side flaws allow an architect to hijack the victim’s browser and manipulate the trust relationship with the application. ##### Cross-Site Scripting (XSS) * Stored: Permanent (comments, profiles). * Reflected: Transient (URL parameters). * DOM: Entirely client-side (manipulating the DOM). * Strategic Bypass: Use URL Encoding (e.g., encoding the entire payload) to bypass filters that only look for plaintext
